## 3. Website Design Direction

Build a premium, immersive, modern 3D-animated portfolio. It should feel
like a professional AI engineer's digital identity, not a generic
developer template.

Visual requirements: - Interactive 3D hero experience. - Smooth scroll
animations and meaningful micro-interactions. - Creative 3D objects and
dimensional elements. - Strong typography and editorial layouts. -
Premium transitions and project presentation. - Responsive layouts for
mobile, tablet, laptop, and desktop.

### 3D and motion requirements

Use Three.js or React Three Fiber only when the approved design
genuinely needs 3D. Possible concepts include an interactive AI-inspired
object, abstract orange 3D sphere, animated geometric structures,
dimensional typography, or depth-based scroll effects.

3D must enhance the experience rather than make it heavy. Optimize
rendering, geometry, textures, and animation loops. Lazy-load
nonessential scenes, provide static fallbacks, support touch devices,
and respect `prefers-reduced-motion`. Keep navigation, headings, project
information, and CTAs as accessible HTML rather than embedding them only
in a canvas.

## 6. Engineering Requirements

-   Use clean, maintainable, reusable TypeScript.
-   Follow Next.js App Router conventions.
-   Use semantic HTML and accessible labels.
-   Provide keyboard navigation and visible focus states.
-   Optimize images and 3D assets.
-   Avoid unnecessary client-side rendering.
-   Implement appropriate loading, empty, and error states.
-   Validate form input on both client and server when a form is

    client code.
-   Optimize metadata, social sharing, and page performance.
-   Do not claim performance scores unless measured.

## 7. Step-by-Step Workflow

**Step 1 --- Project Discovery**\
Inspect the repository, framework, dependencies, folder structure,
existing routes, assets, scripts, and project instructions such as
`AGENTS.md`. Do not modify files during discovery.

**Step 2 --- Planning**\
Prepare the website structure, content strategy, and design direction.
Identify missing facts that need Hasnain's confirmation.

**Step 3 --- Design System**\
Define Cream, Ink Black, and Orange tokens; typography; spacing;
containers; layouts; buttons; cards; responsive navigation; and motion
principles.

**Step 4 --- Foundation**\
Implement approved global styles, fonts, metadata, layout, navigation,
and reusable UI primitives.

**Step 5 --- Sections and Projects**\
Build approved sections in small, reviewable steps. Use only confirmed
project facts and approved assets.

**Step 6 --- 3D Experience**\
Implement the approved 3D concept, optimize it, and provide
reduced-motion and static alternatives.

**Step 7 --- Responsive and Accessibility Review**\
Review mobile, tablet, laptop, and desktop layouts, keyboard
interaction, contrast, semantics, and reduced-motion behavior.

**Step 8 --- Validation**\
Run available lint, TypeScript checks, production build, and relevant
tests. Report exactly what ran and its result. If a command cannot run,
explain why.

**Step 9 --- Documentation and Handover**\
Document implemented features, architecture, routes, components,
decisions, affected files, validation results, placeholders,
limitations, and how to update content.

## 8. Approval and Change Control

**Never modify project files without Hasnain's explicit approval.**

Before each implementation step: 1. Explain what will be done and why.
2. Explain how the change will work. 3. Identify the files/components
expected to be affected. 4. Provide a scoped coding-agent prompt when
useful. 5. Wait for explicit approval before making changes.

Do not interpret general discussion as permission to edit files. Ask
before adding paid services, analytics, databases, authentication,
external integrations, dependencies, or changing architecture. Keep
changes limited to the approved scope.

## 9. Communication Style

Communicate in simple Roman Urdu while keeping code, technical
identifiers, and standard engineering terms in English.

At the start of each step, explain: - What we are doing - Why it is
needed - How it works - Which files may be affected

At the end, explain: - What changed - How it works - Why the approach
was chosen - What was validated - What remains - What comes next

Do not dump code without explaining where it belongs and how it fits the
architecture. Never claim something is tested or completed unless it
actually is.

## 10. Definition of Done

The portfolio is ready for handover when: - Positioning and published
claims are factually approved. - Core sections work on mobile and
desktop. - Project details accurately reflect their status and Hasnain's
contribution. - Navigation and contact links work. - Accessibility
basics are addressed. - Metadata and social sharing are configured. - No
secrets or private client data are exposed. - Available lint,
type-check, build, and tests have been run and reported. - Remaining
limitations and future improvements are documented.

## 11. First Response When This Skill Is Used

Do not start coding immediately.

First inspect the repository if files are available, without modifying
anything. Summarize the existing project, recommend the portfolio
direction and information architecture, identify facts that need
confirmation, and present Step 1 with its purpose and expected output.
Ask for approval before making changes.
